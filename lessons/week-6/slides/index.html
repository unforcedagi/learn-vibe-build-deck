Context: what the AI can actually see

  • Its answer depends on the messages, files and tool results available now.
  • It does not automatically know your audience, preferences or project history.
  • “Improve my site” is weaker than a clear audience, goal and example.
Week 6 · Ongoing context8 / 26

Save project context instead of repeating it

  • Write down what the project is, who it is for, and what should stay true.
  • Keep it short, correct and editable; update it when the project changes.
  • Example: “For nervous first-time visitors. Plain HTML/CSS. Do not invent event dates.”
Week 6 · Ongoing context9 / 26

Automatic loading is tool-specific

  • Codex uses AGENTS.md; Claude Code uses CLAUDE.md.
  • Other tools have their own rules and supported filenames—check yours.
  • In a chat app, paste the context or add it to a Project; it may not read local files.
Week 6 · Ongoing context10 / 26

An index points to deeper context

  • A small index says which files exist and what each is for.
  • Example: docs/facts.md → verified facts; docs/design.md → visual direction.
  • The AI can open the relevant document instead of receiving one giant prompt.
Week 6 · Ongoing context11 / 26

Describe the design, not just the features

  • “Make it better” leaves the visual choices to the model.
  • Name the audience, feeling, hierarchy and interactions you want.
  • Example: “Calm portfolio. Work first, muted colours, clickable project cards.”
Week 6 · Communicate intent12 / 26

Make your feedback observable

  • Give a reference or screenshot; say what to keep and what to change.
  • Instead of “It’s broken”: “Clicking this card should open the project; nothing happens.”
  • Ask for one small change, then compare the result with your intention.
Week 6 · Communicate intent13 / 26

Debugging: find the mismatch

  • A bug is a difference between expected and observed behavior.
  • Reproduce it: what exact actions cause it? Capture the error or screenshot.
  • Ask the AI for a cause and a small fix; rerun the same check afterward.
Week 6 · Check the work14 / 26

Check the experience—not just the code

  • Open it on a phone. Click every important button and link.
  • Try empty input, a strange answer, or a first-time visitor’s path.
  • For a learning tool, check its facts and quiz answers against a trustworthy source.
Week 6 · Check the work15 / 26

When free credits run out

  • Save files and a short note: what works, what failed, what to try next.
  • Use that note to continue in a fresh session or another tool.
  • Reduce the request: one change or one explanation at a time.
Week 6 · Working within limits16 / 26

Folder, repository, website: different things

  • Local folder: files on your own computer.
  • Git repository: those files plus a recorded history of versions.
  • Deployment: a published version that other people can open.
Week 6 · Getting online17 / 26

Commit, push, deploy: three actions

  • Commit saves a version and a message in your local Git history.
  • Push sends your commits to the repository on GitHub.
  • Deploy publishes the project through a host such as GitHub Pages or Vercel.
Week 6 · Getting online18 / 26

Your link must work on someone else’s phone

  • file:///… and localhost:8000 point to your own computer—not a public site.
  • A GitHub repository URL shows source; it may not be the live app URL.
  • Use the deployed HTTPS URL; test it on another device or in a private window.
Week 6 · Getting online19 / 26

A practical path to publishing

  • GitHub Desktop: create a repository → commit → publish to GitHub.
  • Plain HTML/CSS: GitHub Settings → Pages → main branch / root → Save.
  • A framework app may need Vercel: allow repository access, deploy, then test the URL.
Week 6 · Getting online20 / 26

API, connector, MCP: what is the difference?

  • API: a service’s menu of requests that another program can make.
  • Connector: a bridge that lets your AI reach a service or files.
  • MCP: a shared protocol for AI apps to use tools; an MCP server may call an API.
Week 6 · Connections—concept only21 / 26

Access is a choice: read versus write

  • Read access can expose data; write access can change or delete it.
  • Give only the access needed; review changes before publishing or sending.
  • Keep keys, passwords and private data out of public files and repositories.
